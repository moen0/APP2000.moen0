Hytter i turappen

Data om hyttene er beskrevet med TypeScript-interfaces (se oppgave5-hytter.ts). JSON-strukturen har objekter (Hytte), underobjekter (Posisjon, Kontakt) og arrays (fasiliteter, bilder). Nettleseren laster den kompilerte JavaScript-fila.

Hyttekort

Fordeler og ulemper med TypeScript for denne oppgaven

Fordeler

  • Feil fanges på kompileringstidspunkt: Hvis noen skriver hytte.senge i stedet for hytte.senger, stopper tsc oss før koden når nettleseren.
  • Dokumenterende typer: interface Hytte fungerer som en kontrakt for backend, frontend og JSON-formatet samtidig.
  • Autocomplete og refactoring: Editoren foreslår posisjon.hoyde_moh og "rename symbol" oppdaterer alt.
  • Literal-typer: type Hyttetype = "betjent" | "selvbetjent" | "ubetjent" gjør det umulig å sette en ugyldig verdi.

Ulemper

  • Ekstra byggetrinn: tsc / bundler må kjøres før siden fungerer.
  • Ingen runtime-sjekk: JSON.parse returnerer any, og as Hytte lurer bare kompilatoren. For data utenfra trenger vi type guards eller Zod.
  • Bratt læringskurve for nybegynnere: generics og strict null checks kan være frustrerende første gang.
  • Konfigurasjon: tsconfig, module-systemer og DOM-typer må settes opp riktig.

Hvordan koden kan testes

  • Enhetstester (Jest/Vitest): teste typeEtikett, lagKontaktLinje, lagHyttekort mot jsdom - sjekke at riktige klasser og tekst finnes.
  • Schema-validering: Zod-schema for Hytte som brukes for å validere JSON fra API/fil ved runtime.
  • Snapshot-test: gitt et fast datasett, sjekk at generert HTML-struktur er den vi forventer.
  • Type-tester: expectTypeOf (fra Vitest) for å verifisere at signaturene ikke endres uten at tester røder.
  • End-to-end (Playwright): serve siden, sjekke at tre hyttekort vises og at bookingslenka peker riktig sted.
